# v0.1 History and CLI Protocol

Status: development preview. Record `schema_version` and CLI `protocol_version` are versioned independently; both are currently 1. Incompatible changes require a version increment instead of silently changing the meaning of existing records.

## Records

| Record | Fields |
| --- | --- |
| Case | schema_version, id, title, created_at |
| Entry | schema_version, id, case_id, kind, content, references, author, created_at |
| Reference | target_id, relation |

Core generates UUID v4 IDs for Cases and Entries. Queries and references require canonical lowercase, hyphenated UUIDs. Core generates RFC 3339 UTC timestamps. Timestamps do not determine history order.

A new Case request contains only `title`. A new Entry request contains `case_id`, `kind`, `content`, and `author`; `references` may be omitted and defaults to an empty array. Unknown fields and caller-assigned `id`, `created_at`, or `schema_version` are rejected. Successful creation returns the complete persisted record.

| Field | Limit |
| --- | --- |
| title | Nonblank; at most 512 UTF-8 bytes |
| kind, relation | Nonblank; at most 128 UTF-8 bytes each |
| author | Nonblank; at most 256 UTF-8 bytes |
| content | Nonblank; subject to the total record size limit |
| references | At most 128; no duplicate (target_id, relation) pair |

Values are preserved as supplied, without automatic trimming or normalization.

A stdin JSON request may contain at most 1,048,576 bytes. Each Case or Entry generated by Core must also fit within that limit after compact JSON serialization, including generated fields and JSON escaping. JSON Schema `maxLength` counts Unicode characters; Core additionally enforces the UTF-8 byte limits.

## History semantics

- Committed Cases and Entries cannot be updated or deleted through the public API.
- A revision is a new Entry referencing an earlier one, conventionally with relation `supersedes`. It does not hide or delete the earlier record.
- Every reference must target an Entry that already exists in the same Case. Cross-Case references, forward references, and reference cycles are unsupported.
- `kind` and `relation` are open strings. Core does not infer truth, permissions, verification status, or state transitions. `supersedes` does not trigger replacement.
- `author` is an attribution label, not an authenticated identity.
- Each create or append operation is one transaction. Any validation, foreign-key, or storage write failure rolls back that operation.
- SQLite's internal increasing `seq` determines append order. It is not part of the public Entry format.
- Repository does not accept caller-assigned IDs for new records. Database uniqueness constraints also reject duplicate IDs.

## Queries

The CLI provides `case create/get/history` and `entry append/get`. Write requests accept one JSON object on stdin; `case create` also supports `--title`.

History returns:

```json
{"entries": [], "next_cursor": null}
```

`limit` defaults to 100 and must be in 1..=1000. `after` is a positive decimal cursor returned by an earlier page. Use it only with the original database and Case. Entries are returned in ascending append order. `next_cursor` is a string only when another record exists beyond the current page; otherwise it is null.

Pagination is not a frozen snapshot. Later pages may include records committed after pagination began. A final page has no cursor; a continuous history subscription API is left for future work.

The CLI returns `not_found` for a missing Case or Entry. Repository single-record lookups return `None`; history for a missing Case returns an error, distinguishing it from an existing Case with no entries.

## Output and errors

Success: one JSON line on stdout, exit code 0.

```json
{"protocol_version":1,"data":{"entries":[],"next_cursor":null}}
```

Failure: one JSON line on stderr, empty stdout.

```json
{"protocol_version":1,"error":{"code":"not_found","message":"case not found: ..."}}
```

| Error code | Exit code | Meaning |
| --- | --- | --- |
| invalid_input | 1 | Invalid JSON, unknown fields, invalid values, or oversized input |
| not_found | 1 | Requested Case or Entry does not exist |
| invalid_reference | 1 | Target is missing or belongs to a different Case |
| unsupported_schema | 1 | Database schema version is unsupported |
| storage_error | 1 | SQLite operation failed |
| invalid_arguments | 2 | Command-line parsing failed |

Messages are diagnostic text; integrations should use `code`. `--help` and `--version` print plain text.

The database path is explicit CLI configuration, not a record field. Record JSON cannot select internal file paths. The CLI runs with the calling process's file permissions and does not provide sandbox isolation.

## SQLite implementation

The repository uses bundled SQLite with `foreign_keys=ON`, `recursive_triggers=ON`, `synchronous=FULL`, and a five-second busy timeout. Schema creation and version assignment occur in one transaction. `user_version=1`; unsupported versions are rejected without automatic downgrade. Schema upgrades, record imports, and exports are not yet implemented.

`cases`, `entries`, and `entry_references` use primary keys, uniqueness constraints, and foreign keys. UPDATE/DELETE triggers reject accidental overwrites. Anyone with file write access can remove the triggers, so these are not malicious-tampering defenses.

SQLite durability depends on the operating system and filesystem behaving correctly. Tests simulate transaction write failures and reopening connections; power-loss and hardware fault injection have not been performed. Use a local filesystem; this preview has not been benchmarked for large workloads.
